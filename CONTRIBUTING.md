# Contributing to gdal-rs-napi

Thanks for helping. This is a Rust `cdylib` exposed to Node.js through
[napi-rs](https://napi.rs), with GDAL, PROJ and GEOS compiled from source and
linked **statically** into the produced `.node`. The package is pre-1.0; the
public surface is described in [`docs/API-STABILITY.md`](./docs/API-STABILITY.md)
and the roadmap in [`ROADMAP.md`](./ROADMAP.md).

Before starting on something large, open an issue so the shape can be agreed
first. Security reports go through [`SECURITY.md`](./SECURITY.md), not the issue
tracker.

## Ground rules

- Read [`docs/API-STABILITY.md`](./docs/API-STABILITY.md) before touching the
  public surface. Naming is by convention: a blocking call is `xxxSync()`, its
  thread-pool twin is `xxx()` returning a `Promise`, getters are properties
  (their async twin is `xxxAsync`), and enumerations are **strings**.
- `binding.js` / `binding.d.ts` are generated by napi-rs; `index.js`,
  `compat/index.js` and the `*.d.ts` entry points are hand-written and are the
  public contract. Generated does not mean unspecified — a name in
  `binding.d.ts` is public.
- Comments explain **why**, not what. The codebase leans on that; match it.
- One logical change per pull request.

## Prerequisites

| Need | Notes |
|---|---|
| Rust | ≥ 1.98 (MSRV pinned in `Cargo.toml`) |
| Node.js | ≥ 20.17 |
| CMake | ≥ 3.12; 4.x needs `CMAKE_POLICY_VERSION_MINIMUM=3.5` (already in `.cargo/config.toml`) |
| Ninja | required |
| `sqlite3` CLI | required — PROJ shells out to it to generate `proj.db` |
| C/C++ toolchain | MSVC (VS 2022+), or clang/gcc on macOS/Linux |

```sh
# Windows
winget install SQLite.SQLite Ninja-build.Ninja
# macOS
brew install sqlite ninja cmake
# Debian/Ubuntu
sudo apt-get install sqlite3 ninja-build cmake g++
```

Keep MSYS2 / Cygwin / MinGW off `PATH` — `scripts/build.mjs` drops those
directories for you and says which. See *"Three things that will bite you"* in
the [README](./README.md#three-things-that-will-bite-you) before your first
build.

## Build and test

```sh
npm install --include=dev      # --include=dev matters if NODE_ENV=production is set
npm run build:debug            # debug build + asset staging (faster than release)
npm test                       # the whole vitest suite (ts-test/**, native + compat)
npm run typecheck              # tsc against compat/index.d.ts and binding.d.ts
npm run lint                   # cargo fmt --all --check
npm run clippy                 # cargo clippy --release --all-targets -- -D warnings
```

The first build compiles PROJ and GDAL from source and takes tens of minutes;
after that the `target/` cache makes `cargo`-only checks fast. The Rust unit
tests are:

```sh
cargo test --release --target x86_64-pc-windows-msvc --lib   # host triple
```

A `.husky/pre-commit` hook runs `cargo fmt --all --check` on every commit.
Clippy compiles the addon first, so it is a push-time check, not a commit-time
one.

## Adding or changing an API

1. Put the entry point in the right module. Keep `band/`, `dataset/` and
   `vector/` as the napi surface (`mod.rs` holds the types and the `#[napi]`
   surface; the worker `Task`s live in `tasks.rs`); raw glue belongs in
   `raster_io.rs`, `raster_tools.rs`, `programs.rs` and friends.
2. Write a doc comment that says **why** the call exists and what GDAL quirk it
   is accounting for. The doc comment is the documentation source.
3. Take the correct side of the process-wide lock — most operations that do not
   touch a dataset take the shared side; datasets, programs and process-global
   configuration take the exclusive side. See `src/runtime.rs` and
   [`docs/CONCURRENCY.md`](./docs/CONCURRENCY.md).
4. Add a test in `ts-test/` (binding behaviour) and, where the mapping is pure,
   a Rust unit test beside the code. `ts-test/native/types.spec.ts` checks the
   TypeScript declarations against the running binding, so a new member that is
   missing from the declarations fails there.
5. If the surface changed, update `README.md`, `CHANGELOG.md`,
   [`docs/PARITY.md`](./docs/PARITY.md) where it is about `gdal-async` parity,
   and the `compat` layer where the reference has the same call.

## What CI runs

`.github/workflows/ci.yml` builds six targets and runs on every push and pull
request. On `linux-x64-gnu` it additionally runs clippy, the Rust unit tests,
the cross-target `cargo check` arms, the compatibility coverage floor, the lock
benchmark (`scripts/bench-parallel.mjs --min-speedup 1.5`), the documentation
consistency check and the licence check. A separate `checks` job runs
`cargo fmt --all --check` and the TypeScript type-check in about a minute.
Anything red there must be fixed before merge.

## Regenerating the SBOM

`scripts/sbom.mjs` writes a CycloneDX document to `dist/sbom.cdx.json` from the
pinned `Cargo.lock` plus the native components. It is generated in CI and
attached to a release; run it locally with:

```sh
npm run sbom
npm run check:licenses
```
