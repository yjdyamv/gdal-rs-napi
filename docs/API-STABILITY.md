# API stability

What this binding promises, and how its public surface is allowed to change.

The promise is deliberately narrow and mechanical. It exists because the surface
is already large — classes, namespaces, ~150 free functions — and because a
binding that mirrors a C library has a standing temptation to follow the C
library's naming into JS, one `_` at a time.

## What is covered

The public API is what the package's entry points export:

- `index.js` — the loader that points GDAL/PROJ at `assets/` and re-exports the
  generated binding. It is hand-written, so it is where a pure-JavaScript export
  would go (see [Where things live](#where-things-live)).
- `binding.js` / `binding.d.ts` — generated by napi-rs from the `#[napi]` items in
  `src/`. **Generated does not mean unspecified**: the shape of what they export
  is the contract, and a name that appears in `binding.d.ts` is as public as one
  written by hand.
- `index.d.ts` — the type entry point.

Everything else is internal and may change in any release: the Rust modules, the
layout of `assets/`, `__napiBindingTarget`, and anything not reachable from the
exports above.

## Versioning

The package follows semver, and `gdal.apiVersion` reports the package version so
a feature can be probed without parsing anything:

```js
if (gdal.apiVersion >= '0.2.0') { /* the setters are here */ }
```

`apiVersion` is the *binding's* version. It is not `version().gdal`, which is the
GDAL the binding was built against, and the two move independently.

**Pre-1.0 (`0.x.y`) the minor version is the breaking one.** Everything below is
already the intended rule; 1.0 is when it becomes enforceable rather than
aspirational.

## Naming

1. **Verbs first, one name per operation.** A blocking call is `xxxSync()`; the
   same call on the thread pool is `xxx()`, returning a `Promise`. There is no
   `Async` suffix — the absence of `Sync` is what says "async".
2. **The exception is a getter, which has no call to rename.** `band.dataType` is a
   property, so a `band.dataType()` cannot exist beside it, and the rule above has
   nothing to apply to. Its thread-pool twin is therefore `band.dataTypeAsync`, a
   property that hands back a promise — which is the reference's spelling too.
   These exist for the *wait*, not for the work: a getter takes the process-wide
   lock, and while an async read holds it a synchronous getter would stop the event
   loop until the read finished.
3. **Cheap getters carry no async twin.** `band.blockSize`, `layer.fields`,
   `band.getPixel(x, y)` and `band.defaultHistogram()` never touch the disk, so
   there is nothing to wait for beyond that lock — and only the ones that report
   what the dataset already knows have one.
4. **Properties read, methods write.** `band.noDataValue` is a getter;
   `setNoDataValue()` is the writer. A property that can be assigned
   (`band.noDataValue = x`) is *not* the style here: a setter that throws is
   harder to miss than an assignment that silently does nothing.
5. **Namespaces group free functions**: `gdal.config.get`, `gdal.fs.readFile`.

## Indexing

**Resources inside a container are 0-based: `dataset.band(0)`, `layer.field(0)`.**
GDAL itself is 1-based, and this is the one place the binding deliberately does
not follow it.

`RasterBand.id` is the single exception, and the reason it exists: it is GDAL's
own band number, passed through unmodified, so it is 1 for the first band. It is
documented as such at every use site. `RasterBand.index` is the 0-based one.

Layer *ids* (`fid`) are not positions and are never rebased — they are whatever
the driver stores.

## Values

1. **A failure throws.** There is no `{ error, result }` shape and no callback
   style. Async methods reject.
2. **"Absent" is `null`, never `undefined`.** A getter that has nothing to report
   says `null`; a field that is `NULL` in the data is present with the value
   `null`. `undefined` in a return position is a bug.
3. **`void` returns only for calls whose whole point is a side effect**
   (`close()`, `flushSync()`, `setMetadataItem()`).
4. **Errors carry `err.code`** — a stable token such as `GDAL_CPL_FAILURE`,
   `GDAL_BAD_ARGUMENT`, `GDAL_MISSING_PROJ_DATA` — on **both** surfaces. An async
   failure also has the token at the front of its message (`[GDAL_CPL_FAILURE] …`),
   because `napi::Task` pins the status type and the message is therefore where the
   token has to travel; the shell lifts it back into `err.code`, so branch on
   either.
   **GDAL's own class and number are not fields.** `err.message` carries them as a
   prefix — `[CPLErr=3 #1] …` — and `lastError()` reports the same pair as
   `{ class, number, message }`. They are deliberately not `err.gdalClass` /
   `err.gdalNumber`: napi's `Error` carries only `code` (from the status) and
   `cause`, and only the async path passes through the shell at all, so fields on
   every *synchronous* error would mean wrapping the whole exported surface —
   constructors and accessors included — which is exactly what `async-methods.js`
   exists to avoid.
5. **A NUL byte in a string is refused**, not truncated. It cannot survive the
   trip into C, so it is reported as a bad argument.

## Resources

1. **Closing is explicit and idempotent.** `close()` on a dataset frees it and
   invalidates every handle that came out of it — later use throws rather than
   touching freed memory. There is no finalizer to rely on.
2. **A closed handle keeps its cheap identity.** `dataset.path` still reads after
   `close()`; anything that needs GDAL does not.

## Growth

1. **New API is additive.** A minor release adds; it does not rename, reorder or
   re-type.
2. **Widen, don't rename.** When a parameter needs to accept a second shape, add
   an overload — `setProjection(wkt)` gaining a `SpatialRef` overload, not a new
   `setSrs()`. Existing calls keep working unchanged.
3. **Vocabularies are frozen strings.** Field types (`'String'`, `'Integer64'`),
   colour interpretations (`'RedBand'`), resampling names (`'bilinear'`) and
   capability names (`'FastFeatureCount'`) are part of the contract. They are
   matched case-insensitively on input where GDAL's own names allow it, and are
   always reported in GDAL's canonical spelling. `gdal.const` names them, so a
   vocabulary can be referenced rather than retyped — and each value there is
   checked against the runtime. Note that GDAL has two resampling vocabularies,
   and `gdal.const` keeps them apart: `Resampling` (a pixel read, and a warp —
   `nearestneighbour`) and `OverviewResampling` (`nearest`, plus `rms` / `none`).
4. **Numeric GDAL enum codes are not exposed.** `GDT_*`, `OFT_*`, `GCI_*` and the
   rest are numbers in C and strings here, on purpose: a string survives a GDAL
   version that adds an enum value, and it is what `gdalinfo` prints. A caller who
   needs the C codes either has them from GDAL's headers or is porting from a
   binding that exposes them — see [Compatibility](#compatibility).

## Deprecation

1. Mark the item `@deprecated` in its JSDoc, saying what to use instead.
2. Keep it working for **at least two minor releases**.
3. Note it under `## Deprecated` in `CHANGELOG.md` when it is marked, and under
   `## Removed` when it goes.
4. Remove it only in a major release. Before 1.0, a minor release may remove
   something that was never in a tagged release.

## Capability probing

Two calls answer "what can this build do", and they answer different questions:

- **`gdal.info()`** — what the statically linked GDAL was compiled with, straight
  from its `BUILD_INFO`. A capability compiled out is an **absent key**, because
  that is how GDAL reports it.
- **`gdal.features()`** — what this *binding* exposes: a fixed set of booleans,
  always present, so `if (gdal.features().geos)` reads the same way whatever the
  build turned out to be. `gdal.diagnostics()` is the third, narrower one, for
  runtime data paths.

Of the three, `features()` is the one to branch on in application code.

## Compatibility

This binding is **not** a drop-in replacement for `gdal-async`, and does not try
to be through the main entry point. Three differences are load-bearing and will
not change:

| | here | `gdal-async` |
|---|---|---|
| Index base | 0-based | 1-based |
| Async naming | `xxxSync()` / `xxx()`, and `xxxAsync` for a getter's twin | `xxx()` / `xxxAsync()` |
| Assignment | `setNoDataValue(x)` | `band.noDataValue = x` |

A separate adapter entry point is the intended home for that shape, so a port is
an import change rather than a rewrite — see `PHASE1.md`. Keeping the two apart is
what lets this API be designed rather than inherited.

## Where things live

`index.js` is hand-written and `binding.js` is generated, so a new export goes in
exactly one of them:

- **Native** — anything that touches GDAL: classes, methods, functions. Declared
  with `#[napi]` in `src/`; the `.d.ts` and the loader stub are regenerated by
  `npm run build` and must not be edited by hand.
- **Shell** — pure JavaScript with no GDAL behind it: the data-path call in
  `index.js`. Its types go in `index.d.ts`.

Nothing else: a constant table does not need to cross the FFI boundary, and a
GDAL call does not belong in JavaScript.

Anything added to `index.js` that the generated declarations do not already
cover needs a matching declaration in `index.d.ts`, which is hand-written for
exactly that reason.

## Changing this document

These rules are meant to be checked, not admired. `__test__/types.test.mjs`
holds the generated declarations against the **runtime**, both ways — every
declared module export and class member must exist, and every runtime one must be
declared — and the async members are checked per class against `async-methods.js`.
A rule added here that cannot be tested should say so explicitly.
